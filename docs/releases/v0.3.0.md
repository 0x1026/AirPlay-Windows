# AirPlay Windows v0.3.0 — GPU rendering and recording

This release keeps mirrored video on the GPU from decoding through display
and hardware recording, eliminating the previous per-frame CPU readback and
upload in the display path.

## Highlights

- D3D11VA H.264/HEVC decoding with GPU color conversion, shared textures and
  GPU fence synchronization on the same graphics adapter.
- Reused decoder surface views and render targets, plus a one-frame display
  queue to limit accumulated presentation delay.
- GPU-resident H.264/HEVC MP4 recording with hardware encoders that accept
  D3D11 surfaces. Scaling and letterboxing stay on the GPU, including when
  the sending device changes orientation.
- The recording codec status identifies the actual path as **[GPU resident]**,
  **[GPU encoder, CPU pixels]** or **[CPU]**. Explicit GPU recording does not
  silently download GPU-decoded images; Auto can use a compatible fallback.
- Automatic or manual display rotation (0, 90, 180 and 270 degrees), saved
  between launches. Recording preserves the received orientation.
- Generic device labels and square resolution limits for phones, tablets and
  other AirPlay devices. The options show the actual received resolution.
- Custom receiver name in **OPTIONS > Receiver Name**, saved immediately and
  applied to both AirPlay and RAOP discovery without restarting the receiver.
  UTF-8 names, including accented characters, are supported.
- Single application instance: launching again restores and raises the existing
  window instead of starting another receiver on the same ports.
- Disconnect waits for media teardown before clearing the display. Control
  reads are cancellable on Windows, and active mirror connections are shut
  down explicitly. App exit deregisters both AirPlay and RAOP discovery
  services before process termination.
- Completed connection threads are recycled during normal operation, preventing
  native thread handles from accumulating across repeated connections.

- Audio-only playback controls: Play/Pause, Previous and Next through native
  DACP discovery. These actions were validated on an iPhone. Progress remains
  read-only because the tested iOS sender rejects absolute seek requests.

## Using the GPU path

Enable **OPTIONS > Mirror Decoder > GPU decode**, then reconnect the sending
device. Select **Auto** or **GPU** in the recording panel. On a compatible
encoder, the recording status shows **[GPU resident]**. Audio encoding and
writing compressed MP4 packets still run on the CPU.

Extract the Windows x64 ZIP and run `airplay-windows.exe` from the extracted
folder, with the supplied DLLs alongside it. Existing saved settings are retained.

## Validation

Hardware integration tests passed on an NVIDIA GeForce RTX 3080 Laptop GPU:
H.264/HEVC CPU and GPU decoding, live codec/resolution changes, all four display
rotations, full/limited color range, and concurrent display and MP4 recording.
Generated recordings were decoded to verify pixels, letterboxing, AAC audio and
monotonic video timestamps. GPU-resident recording reported zero CPU readbacks;
CPU recording and software-decoded input were also checked.

Local rendering measurements are not end-to-end AirPlay latency measurements.

Socket regression tests cover idle connections, partial request headers/bodies,
cleanup ordering, reconnect, repeated stop/start and blocked sends. Windows
tests also verify bounded handle counts across 200 short-lived connections.
Windows mDNS registration and deregistration callbacks returned success for both services.
Closing the actual app with three idle/partial-request clients completed cleanly
in approximately 0.5 seconds locally. The iOS mirroring indicator after a
receiver-initiated disconnect was validated on an iPhone for mirroring and
music played during mirroring.

Receiver naming was checked with an accented UTF-8 name in saved settings,
the binary `/info` response and successful native registration of both services.
Single-instance checks cover concurrent launches, restoring a minimized window
and launching again after the first instance closes.

## Known limitations

- In direct audio-only mode, the tested iPhone can keep AirPlay selected after
  Disconnect or app exit. Selecting the iPhone speaker manually clears it.
- Absolute seeking is unavailable with the tested iOS sender; progress is
  displayed read-only. Play/Pause, Previous and Next are available in the app.
- Audio playout does not yet schedule PCM against RTP/NTP timestamps. A new
  synchronization implementation is deferred to a later version.
- Hardware validation was performed on NVIDIA; AMD and Intel compatibility
  still needs physical hardware coverage.
